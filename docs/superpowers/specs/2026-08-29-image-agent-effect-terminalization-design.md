# Image Agent Effect Terminalization Design

## Goal

Ensure cancellation and budget expiry cannot terminally finish a run while a v3 provider, artifact, staging, or publication effect remains durably claimed but unresolved.

## Problem

The existing finalization protocol detaches provider receipt settlement and provider-state writes after provider dispatch. It still runs successful-result recovery-bundle preservation, staging transitions, publication lease renewals, and object finalization on the cancelled activity context. A cancellation can therefore discard generated bytes or leave `provider_claimed` / `publication_claimed` state while the parent sees a drained child and persists `cancelled`.

The v3 child also caps `StartToCloseTimeout` at ten minutes even when an authorised `DeadlineAt` permits provider work beyond ten minutes. The cap can expire before the provider deadline and newly reserved finalization grace.

## Decision

Separate provider dispatch from durable effect terminalization:

1. Provider invocation always uses the original activity context and, for budgeted execution, its absolute `DeadlineAt` context.
2. Once a provider outcome is known, all work required to leave a claimed v3 effect in a durable terminal phase runs under the existing bounded `providerFinalizationContext`.
3. The bounded finalization includes recovery-bundle persistence, staging-state transitions, publication lease renewal, deterministic object finalization, result construction, and the final effect transition. It does not start a new provider request or extend the provider deadline.
4. If finalization cannot complete, the activity records the corresponding durable unknown phase (`ProviderUnknown`, `StagingUnknown`, or `PublicationUnknown`) before returning. If no terminal/unknown state can be persisted within the grace window, cancellation remains pending and the run is surfaced as blocked for recovery; it must not be projected as `cancelled`.
5. The parent commits `cancelled` only after every started child reaches a durable published or durable unknown/blocked effect outcome.

The cancellation request still becomes accepted immediately; UI/SSE can show it as pending while terminalization completes or blocks.

## Timeout Contract

For a budget-authorized v3 child with remaining provider window `W`:

- provider invocation deadline remains exactly `DeadlineAt`;
- activity `StartToCloseTimeout` is `W + providerFinalizationTimeout`, without the unrelated ten-minute cap;
- legacy histories retain their former timeout decision using the existing version marker;
- unbudgeted activities retain the existing ten-minute timeout.

This gives a long authorised provider call its full window and always reserves the bounded finalization grace after it. It does not allow a provider invocation beyond `DeadlineAt`.

## Publication Policy

Once `ClaimSlotPublicationV3` has acquired a lease, cancellation does not abandon the claim. The finalization protocol either:

- completes deterministic final object publication and `CompleteSlotPublicationV3`, or
- persists `PublicationUnknown` with the lease/fence details if object outcome cannot be established.

It never marks the run cancelled while a publication claim remains open. Existing lease-recovery behavior remains for non-cancel retry paths.

## Compatibility and Tests

All new scheduling and terminalization behavior is gated by `externalEffectFinalizationPatch`; old histories retain their prior deterministic branch.

Tests must prove cancellation during: successful provider return before recovery persistence; staging finalization; publication claim/object finalization; a provider window greater than ten minutes; and finalization failure. Each test asserts that the final projection is not `cancelled` until the effect has published or persisted a durable unknown/blocked terminal phase.
