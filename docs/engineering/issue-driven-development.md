# Issue 驱动派工规则 V1

本文件是 Issue 驱动派工规则的唯一完整正文，依据 [Issue #309](https://github.com/qq550723504/task-processor/issues/309) 中批准的 V1 落仓。Issue 当前正文仍是具体任务目标、范围、依赖、验收与权限的权威位置。

核心规则：**一个有界执行 Issue，同一时间一个实现负责人，独立分支／worktree，通常一个主要 PR；范围内 review 和 CI 修复留在原 PR，独立跨范围问题才新建 Issue。**

本规则只增加派工和交付流程，不另建架构或安全规则。TDD、架构敏感准入、finding 分类及最多两轮正常架构评审沿用 [AGENTS.md](../../AGENTS.md)；Legacy 处理沿用 [Hard-Cut Policy](../refactoring/legacy-hard-cut-policy.md) 与 [Legacy Register](../refactoring/legacy-register.md)，只有 `EXTRACT | RETIRE`，没有 Compatibility 类别。发现批准依据与适用 guard 冲突时，报告具体冲突及最小处理范围，不降低验收、不自行扩大修改范围。

入口：[执行 Issue 模板](../../.github/ISSUE_TEMPLATE/execution-task.md) · [PR 模板](../../.github/pull_request_template.md)。普通有界任务可填 N/A，不强迫补写 PRD、Threat Model 或 Accepted Risk。

## 1. 信息和决策归属

- 产品／架构文档记录批准的产品决定、领域合同、数据处置和安全边界；AGENTS.md 记录稳定开发规则。
- Issue 当前正文记录本任务目标、范围、依赖、验收和权限；评论保留进展和历史变更，不让执行者从长评论链猜当前要求。
- PR 记录代码差异、review 处置、验证、最终 HEAD 和合并批准。
- 聊天负责启动和必要决策；影响任务的决定由协调方记录到相应权威位置并通知受影响 owner。普通评论、自动评审或标签不是扩大权限的依据。
- 实现 Agent 可更新进度／证据，但不能自行改低验收、扩产品范围或接受新风险。
- 同一事实只维护一个当前版本，其他位置引用；AGENTS.md 不写滚动 SHA/CI/机器状态。

## 2. Issue 粒度与分工

- 父 Issue 跟踪大目标和依赖；执行 Issue 有独立可验证结果。普通有界任务不额外要求 PRD／架构设计。
- 通常一个主要 PR；确需先合同后实现等多个小 PR 时，注明每个切片覆盖的验收，父 Issue 不能被部分交付误关。
- 当前范围的 review finding、CI 失败、漏测和缺陷在原 PR 修；独立 owner/验收/前置问题才另建 Issue。
- 用户决定产品与真实操作权限；协调方拆任务、排依赖和作验收决策；Codex 实现；独立 Reviewer 不同时向实现分支写代码；合并由单一指定执行者操作。

## 3. 开工、并行和恢复

- 开工先核对目标/依据/依赖/实际代码、是否已有任务 PR 或其他实现会话；在 Issue 留一条接单记录：会话标识、分支/worktree、起始 SHA、阻塞。
- 授权任务内的实现、隔离测试、提交、推送、维护 PR 可连续执行，不逐步申请。
- 一任务一个写入负责人和独立工作区；换人先交接远端提交、未提交修改和剩余事项。不得覆盖他人工作或自行改写远端历史。
- 按 owner/合同划分并行范围，不仅按文件划分；公共接口/schema 由单一 owner 负责。测试替身也应基于已确认的窄合同，不能各造一套运行时能力。
- worktree 不等于数据库、队列、浏览器隔离；测试使用任务独立的临时资源。
- 恢复会话、决策改变、依赖合入或开始 review 时重新读当前依据和相关增量。不要求 main 每变就立即 rebase，但依赖变化和最终合并前须核对影响并按需同步。

## 4. 状态与依赖

使用单一状态来源表达 `Backlog → Ready → In Progress → In Review → Done`，需要时 `Blocked`；采用已有看板字段或少量既有标签，不为派工配置额外系统。

- Ready 表示具备开工条件，不代表自动启动或真实操作授权。
- In Review 有可评审交付和明确证据/限制；Done 满足该 Issue 全部验收，代码类通常还需相应 PR 已合并。
- 取消的工作记录取消原因，不能当 completed。
- Blocked 必须写缺失条件、负责 owner、解除条件，及影响开工/某个切片/合并/上线中的哪一层。
- 实施状态、合并准入、生产上线不是同一件事；父目标上线阻塞不自动否决隔离可靠的准备切片。

## 5. Review 与收口

沿用现有 `BLOCKER / IMPLEMENTATION_TEST / BACKLOG / ACCEPTED_RISK / NOT_APPLICABLE`。

- 严重度不是阻塞等级的自动映射；写明受影响 Must 和阻塞层级。
- **IMPLEMENTATION_TEST 表示在实现和验证层收敛、不必重开设计；若当前切片 Must 仍未满足，仍然阻止该切片合并。** 明确现有 PR 模板“do not block implementation”不是带真实缺陷合并的许可。
- Accepted Risk/Not Applicable 必须有批准依据；不能用新标签假装风险已接受，也不能把取消的需求记成已实现修复。
- 每轮先查同根因的相邻成功/失败路径及平台分支，再成批修复，不逐文件 push。
- 最终独立复核检查实际差异及其进入完整切片的调用路径，不只看最新一行。Resolve、CI green、review completed 各自不是完整验收。
- 遵守现有最多两轮正常架构评审规则；这不是代码第三次发现真实 Must 缺陷即可忽略。非阻塞建议不无限重开设计。
- 同 SHA 评审已运行时不重复触发。记录最终实际审核的 SHA，旧 Security Review 不当新 HEAD 认可。

## 6. 权限、合并与关闭

- 默认允许授权独立工作区内实现、隔离测试、提交、推送、创建/维护关联 PR。
- 默认不允许自行关闭 Issue、合并、部署、真实平台 mutation、业务数据/profile/账务操作或变更保护规则；标签、优先级和普通评论不能扩大权限。
- “不保留数据”不等于批准立即删除某环境。
- 合并批准留 PR，绑定 PR 号/最终 HEAD/动作；指定执行者按 expected HEAD 正常合并，不绕过分支保护。批准后 HEAD 变更须重新核验并取得相应授权；本规则不默认提供条件式或管理员合并权限。
- 先完成必须随仓库交付的文档再申请最终批准。最终 HEAD、CI run、批准记录写 PR，不为滚动证据制造新的仓库提交。
- main 变化时核对合并组合与适用检查；合并后报告真实 merge commit 和 main CI，不能用旧基线绿灯冒充组合验证。
- 部分交付用 Refs/Relates to；只有执行 Issue 全部验收满足且取得明确关闭授权时，指定执行者才能关闭；父 Issue 不随子 PR 自动关闭。取消与完成分开。
- merge、生产接线、实际环境操作分别授权；merged 不写成 production accepted。

## 7. 进度与证据

- Issue 在接单、阻塞、进入评审、完成/取消时更新，不每个测试刷屏。
- PR 维护当前完整摘要：Issue、最终 HEAD、验收映射、CI/独立评审、NOT_RUN/限制、剩余阻塞、合并/生产权限。
- 实测、fixture、跨平台编译、真实环境验收分开；证据绑定所验证的 SHA，历史结果不能替代当前验证。
- 用户聊天只需 Issue/PR 编号与必要决策，不要求反复搬运完整报告。


## 8. 场景交叉核验

| 场景 | 应采取的行动 | 收口边界 |
| --- | --- | --- |
| 当前切片 review 发现相邻失败路径漏测或 CI 失败 | 在原 PR 检查同根因路径，成批修复并验证 | 当前 Must 未满足时不得合并，即使分类是 IMPLEMENTATION_TEST |
| 缺少另一个领域 owner 的前置合同 | 为独立 owner／验收问题建关联 Issue，写明依赖和解除条件 | 当前 Issue 保留自己的范围；只阻塞受影响层级 |
| prepared-only 切片已可隔离验证，生产接线仍缺依赖 | 按本切片验收与授权评估合并 | 准备切片可合并不等于允许接线或 production accepted |
| 父目标由多个 PR 交付，本 PR 只完成合同 | 使用 Refs / Relates to，注明覆盖的验收 | 不自动关闭父 Issue，未完成部分继续跟踪 |
| 获得合并批准后 HEAD 因修复变化 | 对新 HEAD 重新核验 CI、评审和相应授权 | 旧 HEAD 的批准或 Security Review 不能沿用为新 HEAD 认可 |
| 产品决定“不保留数据” | 将数据处置决定记录在批准文档 | 未授权具体环境和动作前，不得立即删除真实数据 |

## 9. 启动与迁移边界

Codex 启动指令示例：

> 执行 Issue #<编号>；读取完整正文、引用依据和适用 AGENTS.md，检查既有接单与关联 PR，使用独立工作区；进度写 Issue，验证与评审证据写 PR；不自行合并、关闭 Issue、部署或操作真实数据。

Ready 和 Issue 创建都不会自动启动 Agent；用户将编号交给执行会话后接单。协调方维护当前范围和决策，实现者交付并报告缺失条件。

本规则不改变 #303 的现有收口范围或分支，不要求其重新准入，也不是其合并的新前置；#304/#307/#308 的实现与决策不变。后续新业务派工在 #303 收口后应用本方式。不得为落地规则批量重写既有 Issue/PR，或新增自动派工服务、机器人、状态扫描器、公共 CI、标签/看板配置及保护规则变更。
