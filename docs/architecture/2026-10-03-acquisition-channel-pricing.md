## Product outcome and authority

Product decision (2026-10-03): server-side acquisition uses the proposed **¥0.05 per completed acquisition** price; plugin/local acquisition is free. The user's operation is to submit a 1688 link through the server and inspect the saved product, or to submit an already captured page from the browser extension/local executor and inspect that saved product. A failed or unpublished server operation must not consume a data row; a completed operation consumes one. A replay of the same operation does not consume another. Browser Capture/local executor must not require a data-row balance or consume one. The price is the purchase price of one `DATA_ROW` resource unit (5 CNY minor units), not an instruction to charge the wallet directly for each acquisition.

## Current behavior and root problem

`AcquisitionService` and server `BrowserAcquisitionService` reserve one `DATA_ROW` before provider dispatch, then reconcile against Product's terminal publication evidence. Browser Capture uses the same charge coordinator in `Capture` and `ByKey`, and SRC's publication transaction requires a charge reservation for both public and browser-capture producer kinds. Thus the plugin currently fails with zero data rows and consumes a row when successful. In `BrowserCaptureService.ByKey`, a prepared/publishing operation can be charged, claimed and published **before** the existing `resolveReadOnly` checks its browser-capture fingerprint and producer. A key alone is not authority to reclassify a paid server operation as free.

## Channel and fact ownership

Use the already persisted immutable Product facts: a Browser Capture operation has a nonempty `CaptureSHA256`, a browser fingerprint, and a persisted command with `BrowserAcquisitionProducerKind`, `browser_capture` metadata and the matching capture hash; server operations have the server fingerprint, empty `CaptureSHA256` and `AcquisitionProducerKind` with their provider channel metadata. These facts are authored by the server's separate acquisition endpoints, not by a caller-supplied price/channel flag. A key collision between routes is a conflict and must perform no mutation or resource action. Unknown/malformed/mismatched persisted facts fail closed.

Before **any** Browser Capture `ByKey` claim, publication, or recovery, validate the stored scope, key-derived ID, browser fingerprint, capture hash, command producer, and metadata as one channel-bound operation. The same validation applies to `Capture` replay and read-only recovery. Do not change the persisted operation's channel on replay. A server operation can be resumed only by its server route and remains charge-gated. Retain the current live identity, organization, membership and publication authorization checks; free means no resource charge, not anonymous access.

## Publication and resource protocol

Server public HTTP and public browser retain the existing admission: reserve exactly one `DATA_ROW` for `(organization, ProductAcquisition, operation ID)` before provider dispatch; publish with the existing charge-aware Product transaction; reconcile to consume only from a verified final Catalog publication, or release on a proven terminal failure. Ambiguous provider/publication/response outcomes remain `UNKNOWN` and resume by the original operation, without fresh spending or duplicate side effects. No direct wallet deduction.

Browser Capture/local executor still use the same Product operation, SRC/Catalog transaction, publication receipt and exact readback. Its transaction guard must lock and verify the persisted operation/command/producer/fingerprint **before** Catalog publication and atomically mark the Product operation published with the receipt. It must require **absence** of a Product charge intent/reservation for a new free operation; it never calls Resource `Reserve` or `Reconcile`. The paid guard still requires the bound reservation and writes terminal charge proof in the same transaction. Do not remove the publication guard merely because this channel is free. For a previously charged Browser Capture operation, fail closed and report separately; do not reinterpret historical durable charge facts as free or create a migration in this greenfield task.

Product and Commercial remain distinct consistency boundaries. No new table, fact owner, queue or cross-database transaction is needed. The existing source publication receipt is the terminal evidence. Retries and concurrent calls must converge on the same receipt and Product state. If authorization is revoked or organization context changes, neither path may claim/publish/reconcile for that request. Avoid leaving a free operation indefinitely `publishing` after a successful publication: the same transaction records its terminal state.

## Price configuration and current install

Commercial's existing `Offer` contract already supports `ProductDataRow`, `ResourceDataRow`, `CNY`, integer `UnitPriceMinor`, `PricingVersion`, bounds and status. The approved unit price is **5 minor units per data row**. Add one bounded, versioned server-owned catalog entry via the current Commercial owner initialization/configuration path for a **fresh** installation; do not put a price in a browser request or silently overwrite an operator's existing offer. The purchase quote freezes the catalog version/price, existing wallet order and Resource grant remain the only purchase path. If an installation has no approved active offer, show unavailable and refuse purchase; do not fabricate a purchasable UI state. This change only approves the data-row offer; AI points and store-period prices stay as previously configured/unavailable.

The exact offer identifier and quantity bounds are implementation details within the existing Commercial owner. Its schema-owner initializer is the installation point: use the existing create-only offer path, never `SaveOffer` or serving-runtime writes. Tests must demonstrate that a second initialization does not replace a changed price/version. If another active DATA_ROW offer already exists, initialization must refuse to add a competing price and require an explicit owner decision; it must not rewrite the existing catalog. No mutation of the retained localhost pilots or real data is part of this design/Issue.
