# 设计增补：匿名采集速率治理与出口代理（#514）

**状态**：Draft。**本 PR 只含本文档，不含任何实现**。
速率治理（Part A）与出口代理（Part B）**均未实现**；实现须待本文通过独立架构评审并明确 `IMPLEMENTATION_READY` 之后另行提交。
**基线**：`docs/architecture/2026-09-26-1688-server-public-browser-acquisition-design.md`（冻结基线）
**触发**：真实网络验收显示成功率受**频率触发**的挑战墙限制；用户提出供应商 API 代理 + 每次换 IP + 每次全新 Chromium。

## 1. 观察事实（A5 实测，勿当作推测）

| 观察 | 证据 |
|---|---|
| 拦截按 IP 作用域 | 同一 IP 撞墙 → 冷却后恢复 → 密集请求再撞墙 |
| 挑战页形态 | `https://detail.1688.com//offer/<id>.html/_____tmd_____/punish?...`，标题「验证码拦截」/「请登录」 |
| 触发因素是频率 | 约 10 次密集探测后触发；单次成功采集耗时 2.0s |
| 每次全新浏览器 | **已是现状**：`MkdirTemp` + `LaunchPersistentContext` + `Close` + `RemoveAll`，无跨采集复用 |

## 2. 关键判断

1. **「每次不同 Chromium」无需新增**，现状已满足。
2. **「每次换 IP」提高单请求成功率，但不改变根因**。根因是频率；轮换只是把同一套高频行为复制到更多出口。**因此速率治理必须先于、且独立于代理存在。**
3. **「换 IP + 换浏览器」组合可能反向降低长期成功率**：1688 看到的是大量零连续性的全新客户端集中访问同一批商品页，这种模式在反爬视角下比固定 IP 的重复访问更像爬虫。**此判断目前无实测证据**（出口 IP 不可用），需在代理到位后以 A/B 验证，不得当作已证实。

## 3. Part A：速率治理（**提案，未准入**）

新增 `browser.Throttle`（**待准入后实现**），在**任何浏览器工作之前**限流：

| 参数 | 默认 | 依据 |
|---|---|---|
| `MinInterval` | 20s | 观察到的触发突发远低于此；起步值，可按部署实测调整 |
| `Jitter` | 0.3 | 避免多采集进程同步成规律模式 |
| `ChallengeCooldown` | 10min | 覆盖观察到的恢复窗口；**只有挑战**会触发全局冷却 |

**语义要点**

- **仅**挑战（`ErrChallenge`）→ 进入冷却，后续请求**立即**返回 `ErrThrottled`（不在 handler 内等待十分钟）。
  `ErrRejected`（本文档 Part A 之外、本 provider 自身出网策略拒绝导航：文档超限、重定向到未允许 origin）**不触发**冷却——那是我们自己的策略判定，不是 1688 风控信号；把它当挑战会让一次配置或内容策略失败把此后所有无关采集一起挡在十分钟冷却后，且策略不匹配持续存在时会无限重复。
- 等待装不进调用方预算时**立即拒绝**，而不是让预算耗尽 —— 否则会把「我们自己选择等待」误报成「1688 慢」的 deadline
- 非挑战失败（`ErrUnsupported` / `ErrUnavailable` / `ErrCapacity`）**不触发**冷却
- 采集器把 `ErrThrottled` 映射为**可重试**的 capacity（503），不报 502 SOURCE_UNAVAILABLE

**多采集进程的协调（已定方向）**

冻结基线把准入放在**每个采集进程/容器**内，因此进程内的节流与抖动**不会**跨进程强制 20s 间隔，也不会传播冷却。两种可选做法：

- (i) 以**出口 IP 为键**做跨进程协调（共享速率存储）
- (ii) **约束每个出口 IP 只由一个采集进程使用**

**本文选择 (ii)**：它不需要新增协调服务或共享事实源，符合「不新建 Admission Control 平台 / 第二事实源」的既定边界，且 (i) 引入的共享速率状态本身就是需要独立准入的新持久化事实。代价是**该约束必须由部署保证**，因此：

- 同一出口 IP 不得被多个采集进程同时使用（compose/编排层保证）
- 验证必须覆盖**多实例与重启**场景

**重启安全的归属（补齐 (ii) 的缺口）**

进程内记忆无法告诉重启后的进程「这个出口 IP 十分钟前刚被挑战过」。若新进程立即出网，它会在冷却仍应生效时再次撞墙，抵消全部治理。因此在没有共享状态的前提下，唯一诚实的做法是**启动隔离期**：

- 采集进程启动后进入 `warmup`，**首次出网前静默等待**一个可配置的启动隔离期（默认与 `ChallengeCooldown` 同值）。
- 该延迟**不是**共享速率状态，不需要新事实源或跨进程协调，符合 (ii) 的边界。
- 取舍：它让「刚重启就想立刻采」变慢，但**方向是安全的一侧**——宁可少采一次，不可刚重启就续撞。

> 替代方案「把冷却落盘/共享」已被显式排除：那会引入需独立准入的新持久化事实。

- 验证必须覆盖：启动隔离期内**不发出任何请求**；隔离期结束后首个请求正常放行

> 若未来确实需要同一出口 IP 承载多个采集进程，则 (i) 成为必需，届时需独立架构准入。

**不改**：身份契约（canonical source 仍为 `detail.1688.com`）、`MapAcquisitionEvidence`、SRC-1/Catalog 事实规则、operation 状态机。

## 4. Part B：出口代理（**待确认，不在本次实现**）

### 4.1 两种供应商形态

| 形态 | 机制 | 复杂度 | 备注 |
|---|---|---|---|
| **隧道代理** | 配置单一固定 `host:port`，出口 IP 在其后轮换 | **低**：无池化、无 TTL 过期 | 若支持「会话保持」数分钟，风险量级更低 |
| **提取式 API** | 每次调用返回 `ip:port:user:pass` 列表，带 TTL | 中：需池化、TTL 管理、速率限制 | 池容量 ≈ 并发 × 单次采集时长 |

> **用户决定（2026-09-27）：两种形态都必须支持**，不预选供应商的产品形态。因此实现必须把「出口来源」抽象为一个接口，两种形态各提供一次实现，由配置选择 —— 而不是把某一种形态写死在采集进程里。

### 4.1.1 出口来源抽象（两种形态的共同契约）

采集进程只依赖一个契约，两种形态都映射到它：

```
Acquire() -> Exit{ Endpoint, Username, Secret, ExpiresAt?, SessionKey? }   // 取得一个出口
Release(Exit)                                                          // 用完归还（可为空操作）
```

差异被吸收在实现里：

| | 隧道代理实现 | 提取式 API 实现 |
|---|---|---|
| 取得出口 | 直接返回配置中的固定 endpoint；**会话保持**由 `SessionKey` 表达（同一 key 在窗口内尽量落在同一出口） | 调供应商 API 取一个；`ExpiresAt` 来自返回的 TTL |
| 归还 | 空操作 | 归还池中；若已过期则丢弃而非复用 |
| 池化 | 不需要 | 需要，容量 ≈ 并发 × 单次采集时长，受供应商速率限制约束 |
| 凭据 | 同 Part B 的约束：不得进 argv | 同左；且供应商 API 凭据本身只从环境读取 |

**共同的失败语义**（两种形态一致）：

- 出口来源不可用（API 挂了 / 无可用出口）⇒ `ErrUnavailable` ⇒ **503 ACQUISITION_UNAVAILABLE**，**不得**报 502 SOURCE_UNAVAILABLE
- 取得的出口在浏览器启动前即已过期 ⇒ 视为不可用，**不得**用它启动浏览器
- 单个出口失效（连接被拒）⇒ 只重试一次，换一个出口；仍失败则按该次采集失败如实上报，**不伪造商品**

> 抽象成接口的代价是多一层间接；收益是换供应商、换形态都不需要改采集流程，且两种形态的失败语义只有一处定义、不会各自漂移。

### 4.2 硬性约束

1. **凭据不得进进程命令行。** `--proxy-server=http://user:pass@host:port` 会把凭据写入 argv（进程表 / 容器 spec / 日志可见）。这与我已从采集进程移除 `-credential` 的理由同类，**不得重犯**。
   - 方案：本地无认证转发代理注入上游凭据，Chromium 只看到 `host:port`；或凭据走文件，参数仅含无认证本地出口。
2. **供应商 API 主机必须进入 D12 白名单**，且其不可用必须报 **503 ACQUISITION_UNAVAILABLE**，不得报 502 SOURCE_UNAVAILABLE（否则监控会把供应商故障误判为 1688 故障）。
3. **D12 连接层控制须重新验证**：出口变为代理后，「采集进程无内网 DB 可达」这条要重新证明（配置不当的代理可当跳板）。
4. **D8 资源边界须重定**：现有上限为「每进程并发 2」；轮换会诱导扩进程，需设**全局**并发上限。
5. **轮换不得用于绕过挑战后立即继续高频抓取**：挑战冷却（Part A）优先级高于轮换，二者并存时冷却生效。

### 4.3 不改变的东西

- 商品身份仍为 `crawler/1688/<offerID>`，channel 仍为 `public_browser`；**出口 IP 不参与身份**。
- 采集进程仍无数据库凭据、无数据库网络可达。
- 每次采集仍是全新匿名上下文，用后销毁。

## 5. 验证方式

代理到位后做 A/B，各自在受控窗口内测：

| 组 | 配置 | 观测 |
|---|---|---|
| A | 节流 + 单 IP | 成功率、挑战间隔、恢复时间 |
| B | 节流 + 轮换 IP + 全新浏览器 | 同上 |

**节流在两组中都必须开启**，以隔离「轮换本身」的效果。若 B 组长期成功率不优于 A 组，则不引入轮换。
